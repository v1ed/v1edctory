# Аудит утверждений и исходной базы

Дата проверки: **25 ноября 2026 года**. Документ относится к подготовке разработки форка VIctory на Windows с NVIDIA как целевой платформой и AMD iGPU как дополнительным тестовым устройством.

Проверены публичные исходники, manifests, CLI и документация репозиториев. Сборка и аппаратные испытания на компьютере пользователя не выполнялись. Описание автора проекта считается заявлением автора; оно не становится независимым бенчмарком из-за наличия ссылки. Рекомендации ниже отделены от наблюдаемых фактов.

**Вывод:** оригинальный VIctory можно выбрать основой инструкции по предпочтению пользователя и ради меньшего числа экспериментальных изменений. Старые таблицы FPS смешивали разные GPU, сцены, коммиты и параметры запуска; их нельзя использовать для ранжирования архитектур.

## 2. Прямой DXIL и SSA уже реализованы

**Исправлено.** Ранее VIctory описывался как транслятор через HLSL и DXC, а непосредственная генерация DXIL — как будущая оптимизация. Проверенный VIctory уже строит SSA, анализирует EXEC и ресурсы и самостоятельно формирует DXIL/LLVM bitcode. Это видно в [описании архитектуры][architecture] и [эмиттере bitcode][bitcode].

HLSL → DXIL остаётся описанным основным путём XCL, хотя в нём есть экспериментальные альтернативы. Смешивать архитектуру разных проектов нельзя. Перед назначением агенту задачи «сделать SSA», «добавить прямой DXIL» или «написать shader tests» нужно проверить существующие реализации и сформулировать конкретный недостаток.

Наличие IR само по себе не доказывает качественную оптимизацию. Прямой DXIL также не гарантирует ни правильный результат, ни быстрый машинный код драйвера. Новую архитектуру оправдывает измеренный дефект, который трудно устранить в существующих границах компонентов.

## 3. `--strict` не запрещает пропуск GPU-операций

**Исправлено по CLI.** У `victory run --strict` другое назначение: отключить передачу разрешённых системных вызовов хостовой Windows. `census --strict` изменяет подсчёт покрытия импортов. Политика отсутствующих импортов задаётся отдельно через `--unimplemented trap|zero`; `trap` является значением по умолчанию. Это подтверждается [описанием аргументов][cli] и [реализацией запуска][run].

Следовательно, добавление `--strict` не выполняет требование пользователя «без пропуска неподдерживаемых шейдеров». Оно может остановить полезные предусмотренные обращения к Windows, не устранив ни один пропуск draw/dispatch.

Для требуемого режима нужна отдельная проверяемая политика: неподдерживаемая операция либо исполняется эквивалентно, либо завершает тест диагностируемым отказом. Отсутствие реализации, ожидание компиляции PSO и временная нехватка ресурсов должны различаться. Нельзя объявлять такой режим существующим до проверки его реализации.

## 4. Нулевой код возврата ещё не означает прохождение проверки

**Исправлено по исходникам.** `victory translate` накапливает отказы трансляции или проверки, печатает статистику и может завершиться через `Ok(())`. Прогрев кеша также сообщает количество отказов без обязательной ошибки процесса. Поэтому shell-проверка `$LASTEXITCODE -eq 0` необходима для обнаружения аварии команды, но недостаточна для подтверждения полного покрытия. См. [translate.rs][translate].

При подготовке baseline нужно сохранять числитель, знаменатель, стадии проверки и причины отказов. Для полноценной автоматизации разумно добавить структурированный отчёт и отдельный строгий критерий завершения. Это предлагаемая задача разработки: готовые флаги `--json` или `--fail-on-unsupported` в проверенном CLI отсутствуют.

**Подтверждено ограничение аргументов:** `translate --cache` несовместим с `--validate` и `--list`. Аудит с валидацией и прогрев кеша выполняются раздельно. `--pipelines` создаёт объекты на GPU и тоже должен учитывать очередь аппаратных тестов.

## 5. Зелёный `cargo test` не доказывает наличие эталона

**Исправлено.** В проекте уже есть дифференциальные тесты, сравнивающие результат перевода консольного варианта HLSL с PC-вариантом. Однако часть из них требует `VICTORY_CONSOLE_DXC` и PC DXC. При отсутствии нужного компилятора или устройства возможен ранний выход из теста с сообщением о пропуске. Стандартный итог Rust test harness при этом не обязательно отражает пропуск как отдельный статус. См. [diff_tests.rs][diff-tests].

Нужен учёт реально исполненных проверок: `passed`, `failed`, `not_run`, `unsupported`, причина отсутствия предпосылок. Нельзя автоматически считать консольный компилятор доступным через обычный Windows SDK. Открытое окружение разработки должно честно работать с меньшим уровнем доказательности, а не имитировать наличие закрытого инструментария.

Также существуют синтетические тесты инструкций с CPU-моделью, аппаратным D3D12 и WARP. В [semantics_tests.rs][semantics-tests] описаны источники модели и случаи, где проверяется лишь согласованность двух устройств. Повторное использование этих тестов быстрее, чем немедленное написание полного CPU-интерпретатора GPU.

## 6. AMD iGPU полезна, но не является готовым Xbox oracle

**Уточнено.** Дополнительный AMD-адаптер полезен для сравнительных тестов PC-шейдеров и исследования поддерживаемой стандартной семантики. Но выполнение уже переведённого DXIL на AMD не проверяет напрямую оригинальный машинный код Xbox: общий ошибочный lowering может дать одинаковый неверный результат на AMD и NVIDIA.

Для независимого аппаратного теста конкретной ISA-инструкции нужен механизм запуска подходящего машинного кода с проверенным ABI, состоянием регистров и памяти. Поддержка архитектуры в ассемблере не доказывает поддержку подходящего runtime. Обычная передача HLSL/SPIR-V драйверу тоже не гарантирует выбор именно той машинной инструкции, которую исследуют.

В проверенном VIctory есть ещё практическая проблема: [shader host][shader-host] выбирает первый адаптер, удовлетворяющий эвристике «не software и есть dedicated video memory». Такая эвристика не является надёжным способом выбора UMA. [Runtime host][gpu-host] создаёт устройство с адаптером по умолчанию. Проверенного пользовательского параметра выбора AMD LUID здесь нет.

Первая аппаратная задача поэтому должна добавить явный выбор адаптера и отчёт его возможностей. До этого нельзя уверенно утверждать, что тест выполнялся на iGPU, даже если она включена в BIOS.

## 7. Ограничители и fallback тоже требуют аудита

**Подтверждено.** [README VIctory][readme] описывает пропуск операций с нетранслированными шейдерами и ограничение числа итераций shader loops. Присутствуют диагностические switches, меняющие исполняемую работу. В [описании lowering][emit] также есть ограничения индексов и подстановки null views.

Не всякий clamp ошибочен: определённая API-семантика может предписывать нулевое чтение вне границ. Но защитное изменение поведения нельзя автоматически считать эквивалентом консоли. Для каждого случая нужны исходный контракт, условия применимости и регрессионный тест.

Требование корректности не означает «убрать watchdog». Превышение бюджета исполнения можно завершать явным отказом с диагностикой. Нельзя засчитывать прерванный цикл как успешно выполненный шейдер или измерять ускорение после потери части работы как оптимизацию.

## 8. Отчёт о 93% compute существует, но его выводы были чрезмерно обобщены

[Issue #10 victory-fork][profile] действительно содержит ранее приведённую разбивку времени. Однако измерение выполнялось на RTX 4060 Ti, в диагностическом режиме и с `VICTORY_SHADER_LOOP_LIMIT=32`. Это существенно меняет условия исполнения. Кроме того, суммы отдельных измерений в отчёте отличаются от других агрегированных GPU-показателей.

**Исправленный вывод:** отчёт даёт кандидатов для исследования конкретного коммита, а не доказывает главный bottleneck всех форков. На RTX 5070 нужно получить собственную трассу с зафиксированной корректностью, сценой и настройками. Валидационные и производительные запуски следует разделять: инструментация сама меняет время и иногда расписание работы.

В текущем [коммите fxceless][fork-commit] также прямо указано, что после объединения изменений полный набор тестов не запускался. Более высокий FPS экспериментальной конфигурации не заменяет проверку готового кандидата.

## 9. Время CPU и GPU нельзя просто сложить в бюджет кадра

**Исправлено как инженерная модель.** Ранее приведённый последовательный бюджет из CPU, GPU, памяти и Present допустим только как условная иллюстрация. Реальный конвейер имеет перекрывающиеся интервалы, очереди и зависимости. На устойчивую частоту кадров влияет критический путь и пропускная способность, на задержку — также глубина очередей.

Для цели 30 FPS интервал представления кадров составляет около 33,33 мс. Это не значит, что любые шесть произвольных статей времени должны суммироваться ровно в эту величину. Нужно отдельно измерять CPU critical path, GPU timeline, ожидания, frame pacing и редкие длинные кадры.

## 10. Распакованный шейдер не содержит готового golden output

**Подтверждено с уточнением.** Извлечение кода позволяет изучить инструкции и часть метаданных. Для воспроизводимого исполнения нужны также входные ресурсы, дескрипторы, параметры запуска, состояние стадий и правила сравнения. Файлы игры сами по себе не предоставляют эталон динамического вычисления.

Эталон должен иметь происхождение: спецификация, независимо написанная модель, проверенный аппаратный эксперимент или доступное консольное измерение. Согласие двух реализаций повышает уверенность, но не является автоматическим доказательством полной эквивалентности. Полный реверс ОС Xbox для начала не требуется; неизвестные консольные особенности остаются отдельными исследовательскими задачами.

## 11. Сроки, ускорение агентов и Quick Resume не подтверждены

**Сняты как необоснованно точные оценки:** конкретные сроки достижения стабильных 30 FPS, табличные множители ускорения от ИИ и последовательность гарантированных приростов от отдельных оптимизаций. Аудита критического пути проекта и измеренной скорости команды для таких цифр не было. Планировать следует результаты этапов, зависимости и критерии приёмки.

**Не подтверждена причина Quick Resume:** ускорение после восстановления само по себе не отличает ошибку часов от зависимости части логики от частоты обновлений. Ранее уверенно изложенная причина и вывод о лёгкости снятия FPS-лимита не установлены просмотренными исходниками. Этот вопрос не должен определять архитектуру тестового стенда без отдельного воспроизводимого эксперимента.

## 12. Лицензии и локальные данные

VIctory указывает GPL-3.0-or-later, XCL — GPL-2.0-only. Поэтому перенос чужих патчей нельзя считать автоматически допустимым; происхождение и условия конкретного материала нужно проверить. Это замечание о различающихся исходных лицензиях, а не полноценное юридическое заключение.

[Asset policy VIctory][asset-policy] требует держать игровые и производные данные вне репозитория. В ней отдельно описано исключение BCPack tables, на которое лицензия репозитория не распространяется. Политику не следует заменять заявлением «все файлы дерева лицензированы одинаково».

Проверенный [пример конфигурации][example] существует. [Config loader][config] использует приоритет ENV → TOML → defaults; переменные `VICTORY_GAME_DIR`, `VICTORY_CACHE_DIR`, `VICTORY_DATA_DIR` реальны. Это позволяет разнести исходники, кеши, сохранения и диагностические материалы без изменения платформенного кода.

## Решение для старта разработки

Зафиксировать исходный SHA и инструменты; воспроизвести существующую сборку; получить честный отчёт выполненных тестов; добавить явный выбор GPU; затем реализовать отчёт отказов и политику без молчаливой потери операций. Следующая задача — одна минимальная исправленная семантическая ошибка с независимым регрессионным тестом. Масштабная перестройка архитектуры, отдельный программный GPU и обещание стабильных 30 FPS не являются необходимыми условиями этого первого результата.
