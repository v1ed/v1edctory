# План эталонных тестов шейдеров

Проверка документации: 25 ноября 2026 года. Целевая машина: Windows 11, Ryzen 7 7800X3D со встроенной графикой AMD и RTX 5070. Это план первых задач, а не готовый runner и не отчёт о выполненных аппаратных тестах.

## 1. Что именно проверяет встроенная графика

AMD подтверждает наличие Radeon Graphics с двумя графическими ядрами и частотой 2200 MHz в 7800X3D. LLVM описывает `gfx1036` как RDNA 2 APU с `wavefrontsize64`. Эти сведения не гарантируют, что установленный драйвер откроет необходимые возможности конкретному API. Адаптер, shader model и размер волны проверяются на машине пользователя; target нельзя выбирать только по названию процессора.

iGPU полезен как второй аппаратный исполнитель D3D12-тестов. Однако обычный путь HLSL → DXIL → AMD проверяет программу на уровне API. Он не гарантирует исполнение конкретной исходной инструкции Xbox: драйвер выбирает машинный код самостоятельно. Запуск произвольной AMD ISA требует отдельного механизма загрузки, правильного ABI и состояния GPU.

Для начала достаточно Windows и D3D12. Linux/Mesa — дополнительная исследовательская среда. ROCm/HSA не включается в обязательные зависимости: наличие target в LLVM не означает поддержку runtime, а `gfx1036` отсутствует в проверенной официальной матрице ROCm. Покупка отдельной Radeon до проверки существующего iGPU не нужна.

## 2. Уровни эталона

| Уровень | Что считается ожидаемым результатом | Что он подтверждает | Ограничение |
|---|---|---|---|
| Контракт инструкции | Независимое описание по ISA и тестовые векторы | Что именно требуется сохранить | Спецификация может не описывать консольное расширение |
| CPU-модель | Простой evaluator для выбранных операций | Соответствие реализованной модели | Ошибка модели возможна; её код нельзя копировать из транслятора |
| Независимый HLSL на AMD | Результат вручную заданной операции через AMD-драйвер | Поведение API и дополнительное независимое сравнение | Не доказывает конкретную ISA-инструкцию и ABI Xbox |
| Контролируемый native ISA test | Результат проверенного машинного блока на совместимом AMD GPU | Аппаратную семантику блока в заданном окружении | Runner пока отдельная задача; это не полный Xbox |
| Консольный capture | Достоверные входы, состояние и выходы исходного выполнения | Поведение конкретного консольного случая | Требует доступного и проверяемого источника capture |

Результат транслятора, запущенный и на AMD, и на NVIDIA, полезен для поиска различий драйверов. Совпадение двух таких запусков не исключает общую ошибку трансляции. Метка `golden` должна содержать происхождение результата, область применимости и правило сравнения.

## 3. Сначала переиспользовать VIctory

Для исходной точки `940d32f69b22265690a0b5a15d6ded572ba33baf` уже существуют:

- `crates/victory-shader/src/emit/semantics_tests.rs` — семантические тесты;
- `crates/victory-shader/src/emit/host.rs` — host GPU harness;
- `crates/victory-shader/src/emit/diff_tests.rs` — дифференциальные тесты с переменными `VICTORY_CONSOLE_DXC` и `VICTORY_PC_DXC`.

В проверенном `host.rs` выбор первого адаптера с `DedicatedVideoMemory > 0` способен исключить интегрированную графику. Это условие нужно заменить явным выбором адаптера, а не выдавать существующий harness за готовый стенд AMD/NVIDIA. В `diff_tests.rs` есть ранний выход при отсутствии внешних компиляторов. Успешный процесс после такого выхода не подтверждает выполнение сравнения.

Первые задачи — инвентаризация этих тестов, устранение неоднозначного выбора GPU и явный учёт невыполненных проверок. Не требуется переписывать весь harness. Тесты, которым нужен закрытый консольный компилятор, учитываются отдельно и не блокируют создание открытого синтетического набора.

README описывает `VICTORY_DXIL` для выбора валидатора и запуск shader tests. Перед применением команд сверить их с выбранным SHA. Валидный DXIL означает соответствие правилам целевого представления, а не эквивалентность исходной программе.

## 4. Требования к capability probe

Probe перечисляет DXGI-адаптеры и записывает для каждого имя, vendor/device ID, LUID, признаки software adapter, объёмы памяти и версию драйвера. Выбор аппаратного устройства выполняется явно; молчаливая подмена AMD на NVIDIA или WARP запрещена.

После создания `ID3D12Device` проверить feature level, поддерживаемый shader model и `D3D12_FEATURE_DATA_D3D12_OPTIONS1`: `WaveOps`, минимальное/максимальное количество lanes, `Int64ShaderOps`. Для дополнительных операций запрашивать соответствующие capabilities, а не выводить их из названия архитектуры. Записать наблюдаемое `WaveGetLaneCount()` из маленького compute shader.

`[WaveSize(64)]` проверять только на подходящем устройстве с необходимым shader model и успешным созданием PSO. На NVIDIA нельзя считать `WaveSize(64)` заменой реализации консольной Wave64. Для такой программы нужен корректный путь эмуляции или явный отказ.

Два адаптера используют независимые devices, очереди и буферы. Одни входы загружаются дважды; результаты после fence читаются на CPU. Cross-adapter sharing для первого стенда не нужен. Аппаратные прогоны на одной машине выполняются последовательно, чтобы исключить конкуренцию за ресурсы.

Каждый отчёт хранит SHA исходников, конфигурацию сборки, версии DXC/validator, ОС/драйвер, выбранный адаптер, seed, hashes шейдера и входов, время, validation mode и статус. Изменение драйвера требует повторного подтверждения baseline.

## 5. Независимые синтетические fixtures

Минимальный fixture включает собственный ISA-блок или отдельно заданную семантику, начальные регистры/маски, входные буферы, ожидаемые изменения и неизменяемые области. Обязательно описать допустимые входы, чтобы случайный генератор не превращал неопределённое поведение в ложную регрессию.

Один путь проходит через реальный decoder/lowering/compiler VIctory. Ожидаемые значения вычисляются независимо: вручную проверенными векторами и простым CPU-кодом. Дополнительный HLSL-тест на AMD пишется по контракту операции, а не автоматически из того же IR. Декодирование проверяется отдельными известными encoding-векторами; совместное использование одного decoder уменьшает независимость проверки и отмечается в отчёте.

Общий oracle для всех шейдеров не требуется. Начать с нескольких операций, затем расширять модель по найденным блокерам. Синтетические файлы должны быть воспроизводимыми без игровых ресурсов и закрытого SDK.

## 6. Статусы и строгая приёмка

| Статус | Значение |
|---|---|
| `PASS` | Проверка действительно выполнена, предусловия подтверждены, результат соответствует контракту |
| `FAIL` | Обнаружено расхождение, ошибка API, unexpected crash, повреждение памяти или превышение оговорённого лимита |
| `BLOCKED` | Проверку нельзя завершить из-за отсутствующих данных, инструмента, реализации либо достоверного oracle |
| `UNSUPPORTED` | Выбранный стенд документированно не предоставляет требуемую аппаратную/API-возможность |

Статусы не преобразуются в `PASS`. Отчёт содержит обязательные тесты и выполненные тесты раздельно. Промежуточный инфраструктурный PR может быть принят со своими ограничениями; ветка не объявляется полностью корректной, пока обязательные проверки имеют `BLOCKED` или `UNSUPPORTED`.

Неподдерживаемая операция самой игры должна получить корректную реализацию/fallback либо остановить прогон с диагностикой. Пропуск draw/dispatch, подстановка нуля, урезание размера работы и обрезание shader loop не являются успешным прохождением. Если достигнут защитный предел исполнения, это наблюдаемый отказ, а не нормальное завершение.

## 7. Floating-point, атомики и диагностика

Для целочисленных операций обычно требуется точное совпадение. Для floating-point правило задаётся отдельно: округление, fused/unfused операции, signed zero, NaN/Inf, denormals и flush-to-zero. Допуск разрешается только там, где его допускает исходный контракт; увеличение общего `epsilon` до исчезновения ошибки запрещено. Правила HLSL не всегда равны требованиям конкретной AMD ISA.

Для конкурентных атомиков сравнивать допустимые результаты или инварианты, если порядок не определён. Атомарность сама по себе не заменяет memory barrier. Для wave-тестов не предполагать равенство индекса thread group и lane index без проверенного основания.

Correctness-прогоны используют Debug Layer, выборочно GBV и DRED. GBV изменяет шейдеры и выполнение команд, поэтому performance-прогоны идут отдельно, на том же SHA, без дорогой instrumentation. PIX видит host D3D12; DRED объясняет device removal; ни один из них не доказывает исходную консольную семантику. WARP — дополнительный API-backend с собственными возможностями, не эталон AMD ISA.

## 8. Первые семь задач

1. **Инвентаризация harness.** Зафиксировать SHA, реальные тестовые targets, зависимости и все ранние выходы. Результат: список выполненных и невыполненных проверок.
2. **Явный адаптер.** Добавить выбор по идентификатору и capability report. Результат: два отчёта с разными LUID и отказ при отсутствии запрошенного GPU.
3. **Базовый compute/readback.** Независимый CPU oracle для `uint32` сложения с переполнением, XOR и ограниченных сдвигов. Проверить границы выходного буфера.
4. **Fixture через транслятор.** Синтетический ISA-блок проходит реальный compiler path. Изменение ожидаемого значения намеренно вызывает `FAIL`; неверный encoding отвергается.
5. **EXEC и divergent flow.** Проверить активные/неактивные lanes, сохранение прежних значений и выход из циклов. Явно различать проверку модели и нативной инструкции.
6. **Wave и память.** На поддерживаемом размере проверить cross-lane операции, groupshared/barriers и атомарные инварианты. Для Wave64 на NVIDIA сначала определить контракт эмуляции.
7. **Regression gate.** Один обнаруженный дефект минимизировать до fixture; подтвердить `FAIL` до исправления и `PASS` после на зафиксированном окружении. В отчёте нет скрытых пропусков.
