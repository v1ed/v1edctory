# Hermes: настройка агентов на Windows для GTA6 compatibility layer

Проверено по официальной документации 25 ноября 2026 года. Эта инструкция настраивает процесс разработки; она не подтверждает исправность конкретного коммита VIctory или возможность запуска игровых файлов. Команды рассчитаны на PowerShell и существующую Windows-среду сборки из основной инструкции.

## 1. Выбрать одну основную среду

Для первого рабочего цикла используйте **Hermes native Windows → отдельный git worktree → Windows toolchain → локальная GPU QA**. Native Windows входит в Tier 1 Hermes. Переезд в WSL ради самого агента не требуется. Linux с Mesa/RADV можно добавить позже как самостоятельный стенд, когда появится конкретный тест, которому он нужен. Такой выбор уменьшает число различий между машиной агента и машиной, на которой исполняется D3D12.

Если Hermes уже установлен и работает, начните с проверки версии. Не переустанавливайте рабочую авторизацию только ради этого проекта:

```powershell
hermes --version
hermes profile list
hermes profile show default
```

Для новой установки официально доступны подписанный Desktop-пакет и Windows-скрипт. Команда из документации:

```powershell
iex (irm https://hermes-agent.nousresearch.com/install.ps1)
```

Можно сначала скачать скрипт, просмотреть его и выполнить локально. После установки откройте новый терминал, пройдите `hermes setup` и проверьте модель командой `hermes model`. Source-установщик управляет собственными зависимостями. Не изменяйте его Python через стороннюю Conda. Сохраните версию Hermes вместе с baseline проекта и обновляйте среду между проверяемыми этапами.

Источники: [установка](https://hermes-agent.nousresearch.com/docs/getting-started/installation), [поддержка платформ](https://hermes-agent.nousresearch.com/docs/getting-started/platform-support).

## 2. Создать четыре профиля

На старте достаточно четырех ролей. Это роли в процессе, а не требование постоянно держать четыре модели работающими:

| Профиль | Результат работы |
|---|---|
| `gta6-lead` | Конкретная задача, владелец, критерии приемки; интеграция проверенных изменений |
| `gta6-impl` | Небольшое исправление и воспроизводимая проверка |
| `gta6-review` | Независимое заключение по точному candidate SHA |
| `gta6-gpu` | Последовательные аппаратные прогоны, логи и результаты |

Если `default` — рабочий профиль с нужной моделью, создайте роли так:

```powershell
hermes profile create gta6-lead --clone-from default --description "Plans small tasks, assigns owners and integrates reviewed commits."
hermes profile create gta6-impl --clone-from default --description "Implements one scoped compatibility fix in its assigned worktree."
hermes profile create gta6-review --clone-from default --description "Independently checks semantics and exact candidate commits."
hermes profile create gta6-gpu --clone-from default --description "Runs serialized Windows GPU validation and records evidence."
hermes profile list
```

Если рабочий профиль называется иначе, замените `default` его именем. Клонирование переносит конфигурацию и часть персонального контекста, включая `.env`, SOUL и curated memory. Поэтому просмотрите новые профили и уберите ненужные этому проекту подключения. Не ожидайте, что clone автоматически создаст пустого специализированного исполнителя.

Синтаксис выбора профиля: `hermes -p NAME COMMAND`. Например, `hermes -p gta6-impl chat`. Флаг `-p` стоит **перед** `kanban`, `gateway`, `config` или `chat`. Явное имя исключает влияние профиля, выбранного ранее через `profile use`.

Источники: [команды профилей](https://hermes-agent.nousresearch.com/docs/reference/profile-commands), [содержимое clone](https://hermes-agent.nousresearch.com/docs/user-guide/profiles).

## 3. Найти конфигурацию и согласовать инструкции

Выполните `hermes profile show gta6-lead` и аналогичную команду для остальных ролей. Используйте показанный home профиля. В native Windows корень данных обычно находится в `%LOCALAPPDATA%\hermes`; существующая установка может использовать другой путь. Не копируйте Linux-путь `~/.hermes` в Windows вслепую.

В home профиля находятся его `config.yaml`, `.env` и `SOUL.md`. В SOUL запишите ответственность роли, формат результата и правило передачи задачи следующему исполнителю. Общие требования к корректности, сборке и тестам должны находиться в **репозитории**, чтобы они версионировались вместе с кодом.

Перед добавлением `AGENTS.md` проверьте существующие контекстные файлы. Hermes выбирает тип проектных инструкций в порядке `.hermes.md` → `AGENTS.override.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules`. Более приоритетный файл может скрыть подготовленный AGENTS. Согласуйте новую инструкцию с upstream вместо создания двух конкурирующих наборов правил. SOUL загружается отдельно.

В первой сессии попросите агента назвать прочитанные инструкции, рабочий каталог и SHA. Это простой способ заметить неверный профиль или старое рабочее дерево до редактирования кода.

Источник: [Context Files](https://hermes-agent.nousresearch.com/docs/user-guide/features/context-files).

## 4. Подключить минимальный набор инструментов

Фрагменты `templates/hermes-lead.fragment.yaml` и `templates/hermes-gpu.fragment.yaml` нужно **слить с существующим config.yaml**, а не заменить им весь файл. После слияния должны остаться единственные разделы `toolsets`, `kanban` и `mcp_servers`. Повторяющиеся YAML-ключи могут скрыть ранее заданные параметры.

Для lead используются `file`, `terminal`, `web`, `kanban`. Отдельный filesystem MCP не обязателен: файловые операции уже доступны. `git`, `gh`, компиляторы и тестовые CLI вызываются через terminal. Канбан нужно включать явно; наличие `all` само по себе не заменяет эту настройку.

Microsoft Learn MCP подключается к `https://learn.microsoft.com/api/mcp`. Он полезен для поиска контрактов D3D12 и Windows. При подключении клиент должен обнаружить актуальные инструменты сервера: не фиксируйте придуманные имена методов в промптах.

GitHub MCP в lead-фрагменте выключен по умолчанию. Если авторизованный `gh` уже решает задачу, оставьте его выключенным. При необходимости включите `github_read`, задав `GITHUB_MCP_PAT` в `.env` этого профиля. В YAML остаётся `${GITHUB_MCP_PAT}`, а не сам токен. Подключение использует официальный GitHub-сервер и read-only заголовок. Старый npm-пакет `@modelcontextprotocol/server-github` больше не является рекомендуемой реализацией.

После изменения начните новую сессию или используйте `/reload-mcp`. Сначала попросите найти одну конкретную страницу D3D12 и проверить доступность репозитория. Подключение считается готовым после реального успешного вызова, а не появления строки в конфигурации.

Источники: [Hermes MCP](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp), [toolsets](https://hermes-agent.nousresearch.com/docs/reference/toolsets-reference), [Learn MCP](https://learn.microsoft.com/en-us/training/support/mcp-developer-reference), [GitHub MCP](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md), [архив старой реализации](https://github.com/modelcontextprotocol/servers-archived/blob/main/src/github/README.md).

## 5. Настроить GPU-профиль

Оба дополнительных GPU-сервера в шаблоне выключены. Включайте каждый после установки соответствующей программы и отдельной проверки подключения.

**PIX:** шаблон использует stdio-сервер `PixTimingCapturesMcp.exe` из PIX 2610.28. Проверьте фактический путь к exe; версия каталога может отличаться. Этот сервер работает с Timing Captures. Его наличие не означает автоматической проверки Xbox ISA или всей семантики кадра.

**Nsight Graphics:** установите версию, содержащую MCP Preview, затем вручную запустите `ngfx-mcp.exe` из `host/windows-desktop-nomad-x64`. Workflow-интерфейс доступен по `http://127.0.0.1:7661/mcp`. В шаблоне указан именно он. Preview-интерфейсы могут меняться: сохраняйте версию Nsight вместе с capture и результатом анализа.

Выдавайте инструменты запуска захватов профилю `gta6-gpu`. Запуски на AMD и NVIDIA, PIX и Nsight выполняйте по очереди. `supports_parallel_tool_calls: false` ограничивает вызовы в клиентском соединении, **не создает глобальный GPU mutex**. Для надежной автоматизации нужен единственный QA-runner либо общий межпроцессный замок. Не включайте два инструмента захвата в один запуск без отдельной проверки их совместимости.

В отчете различайте: тест корректности, debug-validation, захват для диагностики и чистый performance-run. Результаты скорости с включенной GPU validation нельзя напрямую сравнивать с обычной release-сборкой.

Источники: [PIX 2610.28](https://devblogs.microsoft.com/pix/pix-2610-28/), [Nsight automation](https://docs.nvidia.com/nsight-graphics/UserGuide/automation.html).

## 6. Выбрать владельца dispatcher

В этой схеме выбранный владелец — `gta6-lead`. Именно его `config.yaml` содержит ограничения параллельности. На этапе bootstrap шаблон оставляет `dispatch_in_gateway: false`: первую задачу запускайте явно через one-shot dispatch. Настройки в произвольном worker-профиле не меняют уже работающий scheduler другого gateway.

Если существующий `default` gateway уже управляет другими проектами, можно сохранить его владельцем: тогда согласуйте Kanban-настройки в конфигурации **фактического владельца** с остальными проектами. Не запускайте второго владельца автоматически и не сочетайте ручную отправку с активной фоновой отправкой той же доски. Для первой проверки выберите одного владельца и один способ запуска. У остальных gateway-профилей должно быть `dispatch_in_gateway: false`.

После успешного первого цикла для фоновой работы установите `dispatch_in_gateway: true` только у единственного выбранного владельца. В этой схеме затем выполняется `hermes -p gta6-lead gateway start`. Команда `kanban daemon --force` для новой настройки не нужна. Если gateway уже запущен, измененную конфигурацию следует применить штатным перезапуском после завершения активной работы. При работающем фоновом dispatcher используйте его очередь; не дублируйте bootstrap-команды ручной отправки.

Источник: [Multi-gateway deployment](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-multi-gateway).

## 7. Создать доску и первую задачу

Сначала убедитесь, что необходимые инструкции и task specification закоммичены. Новое worktree не получает незакоммиченные изменения из соседнего каталога. Создайте отдельное рабочее дерево средствами Git из основной инструкции и проверьте его SHA. Ниже предполагается, что `C:\dev\gta6\worktrees\MS000` уже существует и содержит закоммиченное ТЗ `docs/tasks/MS000.md`.

```powershell
hermes -p gta6-lead kanban boards create gta6
$env:HERMES_KANBAN_BOARD = 'gta6'
hermes -p gta6-lead kanban boards switch gta6
hermes -p gta6-lead kanban boards show
hermes -p gta6-lead kanban --board gta6 diagnostics
$TaskWorkspace = 'C:\dev\gta6\worktrees\MS000'
if ([string]::IsNullOrWhiteSpace($BootstrapSha)) { throw 'Сначала зафиксируй BootstrapSha из шага 9 основной инструкции' }
$TaskBaseSha = (git -C $TaskWorkspace rev-parse HEAD).Trim()
if ($TaskBaseSha -ne $BootstrapSha) { throw "Неверный worktree HEAD: $TaskBaseSha; ожидался $BootstrapSha" }
git -C $TaskWorkspace status --short
$TaskBody = "Expected base SHA: $TaskBaseSha. Read committed project instructions and docs/tasks/MS000.md. Verify HEAD equals the expected SHA before editing. Record tool versions and supported build commands. Reproduce baseline; report blockers and evidence. Route GPU tests to gta6-gpu. Do not optimize or change GPU semantics."
hermes -p gta6-lead kanban --board gta6 create "MS000: reproduce baseline" --assignee gta6-impl --workspace "dir:$TaskWorkspace" --body $TaskBody --max-retries 1
hermes -p gta6-lead kanban --board gta6 dispatch --dry-run
hermes -p gta6-lead kanban --board gta6 dispatch --max 1
```

Если доска уже существует, пропустите создание. После `create` сохраните возвращенный task ID. Команда `--body` документирована; наличие `--body-file` у Kanban здесь не предполагается. Длинное ТЗ храните отдельным закоммиченным файлом и укажите его путь в body. Проверяйте синтаксис установленной версии через `hermes kanban create --help`.

В этой PowerShell-сессии `HERMES_KANBAN_BOARD` явно закрепляет доску. Порядок выбора — CLI `--board`, environment, current pointer, `default`. Desktop-выбор не заменяет CLI-настройку. Перед отдельным запуском lead ещё раз проверьте фактическую доску и не создавайте повторный MS000: передайте сохранённый task ID и ожидаемый SHA в `prompts/START_LEAD_RU.txt`. После перезапуска PowerShell возьмите сохранённый bootstrap SHA из отчёта; не присваивайте его из потенциально неверного task worktree ради прохождения проверки.

Для наблюдения используйте `show`, `runs` и `tail` с полученным ID. Первый успешный цикл должен доказать правильность профиля, workspace, сборки и передачи отчета. Отсутствующие зависимости — результат диагностики, а не основание молча менять цели задачи.

Источник: [Kanban CLI](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban).

### Что должно быть в первом отчете

Попросите исполнителя разделять наблюдение и предположение. Например, успешное обнаружение двух адаптеров подтверждает доступность драйверов для тестового приложения, но само по себе не подтверждает возможность запуска машинного кода консольного шейдера. Успешная сборка подтверждает совместимость исходников с выбранным инструментарием, но не правильность рендеринга. Такое разделение полезнее большого итогового сообщения с общим словом «готово».

В отчете должны быть исходный и конечный коммиты, точная команда запуска, путь к артефакту, выбранный адаптер, использованный режим проверки и конкретный результат. Если какой-то пункт не проверялся, он остается непроверенным. Не заменяйте отсутствующий аппаратный прогон результатом компиляции или утверждением другого агента. Отсутствие ошибок в логе также не превращается автоматически в доказательство семантической эквивалентности.

При недоступной внешней документации агент может продолжить анализ локального кода, указав ограничение. При недоступной видеокарте можно закончить подготовку теста и передать его в аппаратную очередь. Это позволяет сохранять полезный прогресс без создания фиктивного положительного результата. Самостоятельные изменения контракта теста, допустимых отклонений или эталонного вывода должны отдельно отражаться в ревью.

Для начала оставьте мало одновременно выполняемых задач. Увеличивайте параллельность после измерения времени сборки, потребления памяти и длины очереди аппаратных проверок. Если проверка кандидата занимает больше времени, чем написание исправления, дополнительные исполнители будут преимущественно накапливать непроверенные изменения. Предпочтительнее завершить короткий цикл до интеграции, затем брать следующую независимую задачу.

## 8. Первый цикл разработки

После baseline выберите один минимальный дефект с известной ожидаемой семантикой. Исполнитель сохраняет reproducer и изменение в своей ветке. Reviewer получает точный candidate SHA, затем GPU-профиль выполняет согласованные тесты того же SHA. Только после этого lead интегрирует изменение. Незакоммиченный diff не заменяет идентичность проверяемого кандидата.

Не ставьте первой задачей «переписать весь memory manager» или «сделать 30 FPS». Подходящая первая задача — воспроизводимый тест одного контрактного нарушения, явная диагностика конкретного unsupported-path либо проверка перечисления двух адаптеров. Для исправления требуется ожидаемый результат, для инфраструктуры — наблюдаемый критерий работоспособности.

Агенты работают с карточками через `kanban_*` инструменты; человек использует CLI. `CHANGES` означает возврат конкретных замечаний в существующий цикл. Не создавайте вместо него независимую реализацию с потерянным контекстом. Названия `PASS`, `CHANGES`, `BLOCKED` можно использовать в отчете, но состояние карточки меняется штатными операциями системы.

При `profile_scope_mismatch` проверьте выбранный профиль, версию клиента и backend. Известен аналогичный Desktop-дефект, однако это не диагноз всех ошибок назначения. Не отключайте проверку scope и не правьте SQLite вручную. Сохраните CLI diagnostics и точный ответ интерфейса.

Источники: [worker lanes](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-worker-lanes), [issue с profile scope](https://github.com/NousResearch/hermes-agent/issues/138761), [gateway scope](https://hermes-agent.nousresearch.com/docs/developer-guide/gateway-internals).

## Критерий готовности к началу работы

Окружение готово, когда агент из назначенного профиля видит правильный SHA, читает проектные инструкции, выполняет подтвержденную сборку, сохраняет проверяемый отчет и передает его reviewer; GPU QA при этом запускается последовательно на явно выбранном адаптере. Остальные серверы и роли добавляйте по мере появления задач, которые без них действительно не решаются.
